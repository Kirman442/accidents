# Подготовка Parquet и Arrow на десктопе

Скрипт работает с проверенным `data/prepared-2020-2025/`, без Supabase и изменений приложения. По умолчанию обрабатывает все 2020–2025 годы и все 16 земель. Подготовленный CSV/JSON, официальные ZIP/XLSX и существующие результаты не изменяет. Незавершённый запуск оставляет `.binary-staging-*`; только успешный запуск переименовывает его в готовую папку с `manifest.json`.

## Запуск

Открыть `RUN_PREPARE_BINARY.cmd` в корне UAD. Нужен установленный Python 3.10+ и интернет для первой установки PyArrow. Запуск создаёт отдельное окружение `data/.venv-binary` и устанавливает только `pyarrow==25.0.1`; глобальные библиотеки не меняет. Затем запускает проверки и весь экспорт. Результат — новая папка `data/binary-2020-2025-ДАТА-ВРЕМЯ`, журнал — `data/binary-prepare-ДАТА-ВРЕМЯ.log`.

Свой Python можно указать из PowerShell:

```powershell
./scripts/run_binary.ps1 -Python 'C:/Path/Python/python.exe'
```

При готовом окружении повторная обработка не требует интернета: `./scripts/run_binary.ps1 -SkipInstall`. Если открывать из проводника, CMD ждёт нажатия клавиши после завершения. Для автоматизации использовать PowerShell или Python напрямую.

Для другого компьютера перенести `RUN_PREPARE_BINARY.cmd`, папки `scripts/`, `tests/`, `docs/` и весь `data/prepared-2020-2025/`. Одного клона Git недостаточно: исходные подготовленные данные исключены из Git. Окружение `.venv-binary` на другом компьютере создать заново через запускной файл, не копировать старое.

Прямой запуск и проверка на одном году/земле:

```powershell
./data/.venv-binary/Scripts/python.exe -B -X utf8 scripts/prepare_binary.py --years 2025 --lands 5 --output data/binary-test-2025-05
```

Выходная папка не должна существовать. `--input` позволяет указать перенесённую подготовленную папку; относительный `--output` разрешается относительно текущей рабочей папки. Полный набор содержит 1 543 886 ДТП; значения не удаляются по повторяющемуся исходному UID.

## Все варианты по умолчанию

Каждый год/земля экспортируется в девять вариантов с одной и той же схемой, строками и порядком:

- `parquet/zstd3/YYYY/uland_NN.parquet`: ZSTD level 3.
- `parquet/zstd10/YYYY/uland_NN.parquet`: ZSTD level 10.
- `parquet/snappy/YYYY/uland_NN.parquet`: Snappy для сравнения компромисса скорости/размера.
- `arrow/file/YYYY/uland_NN.arrow`: Arrow IPC file; плюс `.arrow.gz` и `.arrow.br`.
- `arrow/stream/YYYY/uland_NN.arrow`: Arrow IPC stream; плюс `.arrow.gz` и `.arrow.br`.

Arrow IPC без внутреннего сжатия для совместимости с Arrow JS 19. Gzip level 9, Brotli quality 6 сжимаются снаружи. Для браузера сервер должен отдавать соответствующий `Content-Encoding: gzip`/`br` либо загрузчик обязан явно распаковать содержимое. Суффикс файла сам по себе этого не обеспечивает. Нельзя передавать сырые сжатые байты прямо в `tableFromIPC`. Для простого хостинга предусмотрен обычный `.arrow`. На сайт впоследствии публикуется выбранный вариант, а не все экспериментальные дубликаты.

Parquet имеет row groups 16 384 строки и статистику колонок; Arrow — batches до 16 384. Размеры настраиваются через `--row-group-size` и `--batch-size`. Последняя неполная порция сохраняется. Колонки низкой кардинальности используют словари Parquet; Arrow остаётся без dictionary-кодирования для простого прямого доступа к числовым буферам. Профили настраиваются `--parquet-profiles`, `--arrow-kinds`, `--arrow-encodings`, `--brotli-quality`.

## Схема и точность

Геометрия `geometry` — `FixedSizeList<Float64,2>`, пары `[longitude, latitude]`, WGS84/EPSG:4326. Координаты округляются до **пяти знаков**, Float64 не добавляет погрешность Float32. Округление только геометрии; мощности/автопарк/другие атрибуты не округляются. `--coordinate-decimals 6` позволяет сделать отдельный набор для сравнения. В manifest записываются максимальные изменения долготы/широты и оценка смещения в метрах. Это прикладной Parquet с Arrow-совместимой геометрией, без заявления соответствия стандарту GeoParquet.

В одном файле находятся координаты и все атрибуты карты/фильтров/аналитики: год, земля, исходные районный/муниципальный коды, месяц/час/день недели, категория, тип/характер, свет, дорога и шесть флагов участников. Исходный UID — строка (нули, большие значения, внутренние пробелы и повторы сохранены). Уникальный `record_id` — UInt32; текущие ID помещаются точно. Категории/флаги — UInt8, год — UInt16; геокоды — строки. Не смешиваем ID и флаги с координатами в общий Float32-массив.

`archive/accidents_YYYY_full.parquet` сохраняет все исходные подготовленные поля, включая **полные координаты**, source_row/source_oid, LINREF и PLST. Это общий годовой архив, не стартовый файл карты. Runtime и архив связаны record_id и контрольной суммой входного manifest. ID воспроизводим для идентичного исходника/порядка, но не гарантирован между пересмотренными изданиями.

Автопарк `fleet_snapshots` и показатели `land_year_indicators` также создаются во всех девяти вариантах. Их исходные CSV и `accident_summaries.json` копируются побайтно в `analytics/`. Маленькие сводки позволяют показать межгодовую аналитику без загрузки всех точек. Районные коды не означают проверенную связь с регистрационными районами KBA; первоначальная связь автопарка только по землям.

## Проверки и отчёт

До обработки проверяются SHA256 и размеры подготовленных входов. Проверяются домены атрибутов, порядок/уникальность record_id, число строк каждого года/земли и конечность координат. **Каждый** Parquet/Arrow считывается обратно и сравнивается по всем значениям, типам, метаданным и порядку. Внешние сжатые Arrow распаковываются и сверяются также с исходными IPC-байтами. UID не становится ключом дедупликации.

`manifest.json`: генерация, версии/параметры, схемные метаданные внутри файлов, список относительных путей, SHA256/размеры/строки, смещение координат, суммарные размеры каждого профиля. `size-report.csv`: те же размеры и локальные времена записи/обратного чтения. `logical_arrow_bytes` — объём логических Arrow-данных, **не пиковая память браузера, процесса, worker или GPU**. Замеры чтения — одиночные локальные проверки, не бенчмарк первого появления карты. Готовый пакет не означает проверенную работу браузерного загрузчика или публикацию.

Обрабатывается один год за раз, внутри него земли последовательно; все шесть лет не удерживаются в памяти одновременно. Нет широкого пула процессов, имитирующего браузерные workers. Для первого запуска требуется запас свободного диска под все сравниваемые варианты; фактический размер показывает отчёт.

## Зафиксированные предложения для приложения

Один интерфейс и общая логика фильтрации с альтернативными источниками Supabase и файлов. Основной кандидат — статические файлы, независимые от паузы Supabase Free. Четыре параллельные загрузки, постепенное отображение земель выбранного года, обработка в workers, бинарные атрибуты deck.gl. Не загружать все годы ради выбранного года.

Сравнить Arrow (весь файл земли) и Parquet (по возможности сначала geometry/record_id, затем атрибуты **из того же файла**). Частичная сеть требует работающего HTTP Range и проверенного читателя: выбор колонок после полного скачивания не уменьшает трафик. В charging-points 0.6.1 синхронная проекция не работала в проверках; это нельзя молча переносить. IPC stream позволяет читать порции, но не гарантирует все координаты раньше атрибутов. Arrow FFI — отдельный эксперимент с контролем владения/времени жизни WASM, не обещание zero-copy всего пути.

Сравнение в браузере: одинаковые строки, атрибуты и точность; отдельно первые точки, готовность фильтров, полная загрузка, переданные байты и память. Контроль итогов фильтров/аналитики и отмена старого года. Изменение приложения, базы и публикация — следующие этапы.

Источники API: [PyArrow Parquet writer](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.write_table.html), [Arrow IPC options](https://arrow.apache.org/docs/python/generated/pyarrow.ipc.IpcWriteOptions.html). Наблюдения проекта: charging-points README, Step20–26; реализация Arrow mobile-network-map проверена на cb4b289.

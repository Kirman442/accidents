# Разбор аудита 02 — карта, точки и агрегация

13.10.2026. Прочитан полный отчёт 02, изучены helpers, расчёты CVD и оба HTML-макета. Проверены актуальные FilterMap.jsx, files.css, runtime.worker.js, selectTable и локальный HexagonLayer 9.1.8. Изменения приложения не выполнялись.

## Вывод

Постоянную геометрию карты принимаю как требование. Постоянная информационная панель предпочтительна для desktop: сначала сводка отбора, затем карточка ДТП. Агрегация полезна на масштабе страны, но это новый аналитический режим, а не просто изменение CSS. Конкретные цвета, радиусы, zoom-пороги и пределы шкалы пока не подтверждены реальными данными.

## Результат проверки макетов

При ширине страницы 1265 px проверены open / long content / close в split и overlay — шесть сценариев. Размер карты и положение условной метки не изменились: split 835,9×480 px, overlay 1217×480 px, смещение 0 px. Прототип работает в пределах собственной задачи. Он не проверяет реальные тайлы, GPU, отмену запросов, MapLibre viewState, проекцию координат или суммирование ДТП.

В CVD-макете большие образцы различимы, маленькие точки существенно менее убедительны. Это визуальное наблюдение, не измерение различимости пользователями. JSON содержит 36 диагностических случаев и минимум ΔE76=16,13; не считать его гарантией читаемости точек на дорогах и подписях тайлов. Мобильный viewport инструментом фактически не изменился — мобильная приёмка не проведена.

## Что принять

- Постоянный размер области карты при открытии, закрытии и смене карточки. В актуальном files.css .with-card всё ещё меняет колонки, а до 1100 px — высоту карты: проблема подтверждается кодом.
- Desktop-панель присутствует с первого render. До выбора показывает число ДТП, последствия, текущий отбор и единицы отображения; после выбора — существующую карточку. Закрытие возвращает сводку. Внутренний скролл панели не меняет размеры карты.
- Ориентир 70/30, но с ограничением ширины панели. Точная доля зависит от итоговой ширины страницы; аналитические страницы и карта могут иметь разные пределы ширины.
- Разные понятия «число ДТП в ячейке», «доля тяжёлых последствий», «ДТП/км²». Не называть их риском поездки. Большое число в городе само по себе не означает повышенный индивидуальный риск.
- Фильтрация до агрегации, один вклад на одно ДТП, сверка суммы ячеек с result.count, слияние межземельных ячеек, отмена устаревших результатов и учёт дополнительной памяти.
- Разделение пустой ячейки и нулевой доли, точные подписи категорий ДТП вместо числа пострадавших. Коды категорий 1/2/3 нельзя усреднять как численную тяжесть.

## Что скорректировать или отложить

| Предложение | Рекомендация |
|---|---|
| Фиолетовая тяжесть на карте при розовом/охре/бирюзе в аналитике | Не утверждать сразу. Сравнить оба варианта на настоящих тайлах и с карточкой. Для исходной версии предпочитаю единые семантические цвета категорий; фиолетовая шкала остаётся кандидатом. Это вопрос согласованности, не утверждение, что монохромная шкала неверна. |
| Радиусы 1 / 1,15 / 1,30 по тяжести | Не внедрять вместе с первым перекрашиванием. Они выделяют тяжёлые ДТП, но одновременно меняют визуальный вклад категорий. В легенде нужно явно объяснить смысл размера. |
| Zoom 11 / 10,5, размеры 5 км / 2 км / 750 м | Проверить на стране, городе и сельском районе. Гистерезис хорош, конкретные значения не универсальны. |
| Пределы 500 / 100 / 25 ДТП | Не считать готовыми порогами. Рассчитать распределения реальных counts и долю насыщенных ячеек; сохранить единые пороги для сравнимых размеров ячеек. |
| Сначала GPU HexagonLayer, затем H3 | Для рабочего режима с карточкой ячейки предпочитаю сразу прототип H3 в workers. GPU HexagonLayer оставить быстрым визуальным экспериментом, чтобы не реализовывать два разных пути сводок и picking. |
| Heatmap как ещё один основной режим | Отложить. Ячейки и точки уже решают две ясные задачи; сглаженный слой добавит другую легенду и трактовку, не давая точной сводки места. |
| Hover-tooltip с деталями каждого ДТП | Сначала проверить полезность. Данные описания сейчас в workers; не запрашивать их на каждое движение мыши. Текущая карточка уже даёт детали кликом. |
| Запрет любого fitBounds/flyTo | Применять к открытию/смене карточки. Явные команды пользователя «Приблизить» или «Показать землю» могут менять вид карты. |

## Дополнительное ограничение, которого не хватает в плане MVP

В локальном HexagonLayer 9.1.8 масштаб преобразования радиуса в общие координаты вычисляется от центра bounds текущих данных (_updateBinOptions). Если подавать заново упакованные filteredData, bounds могут измениться, вместе с ними — сетка. Это риск для сравнения «те же ячейки до и после фильтра», даже если pan не меняет её. До использования GPU-варианта нужна проверка устойчивости сетки при смене земли, года и фильтров. Фиксированные H3 ID позволяют сформулировать требование однозначно.

GPU picking предоставляет count, но pointIndices доступны только для CPU-агрегации; документация [HexagonLayer](https://deck.gl/docs/api-reference/aggregation-layers/hexagon-layer) это подтверждает. Поэтому нельзя обещать готовый список ДТП в ячейке от одного GPU picking. Нужен worker-запрос либо заранее сохранённая принадлежность к H3.

Без заданного colorDomain цвета Heatmap зависят от текущего viewport; [документация HeatmapLayer](https://deck.gl/docs/api-reference/aggregation-layers/heatmap-layer) подтверждает ограничение. Даже фиксированная шкала не превращает сглаженную картинку в точный счётчик происшествий внутри круга.

## Как внедрять по частям

1. Сначала постоянная панель и управляемый viewState. Один canvas остаётся в DOM; ни наличие selection, ни loading/error не меняют grid и высоту карты. На desktop принимать по rect карты и viewport.project, а не только по условной метке. Мобильную панель отдельно проверить: боковая колонка там не помещается.
2. Вместе с общей темой обновить цвет точек, кольца выбора и контуры земель. Сохранить существующие filters/picking/ids и сначала одинаковый размер точек. Выбор цветовой схемы тяжести согласовать отдельно.
3. Сделать отдельный прототип агрегации на реальных данных: фиксированная H3-сетка, counts трёх категорий, текущие фильтры. Проверить сумму всех ячеек, пересечение земель, пустой отбор, быстрые смены фильтров, память при бюджете 32/100 МиБ. Не обещать производительность до измерений.
4. После сравнения режимов согласовать «Авто / Ячейки / Точки», масштаб перехода и легенду. Панель ячейки — сводка count/категории/фильтры, отдельная команда приближения; карточка ДТП остаётся отдельным видом той же панели.

Для категориальных точек main thread сейчас получает только ids и positions; категории остаются в workers. Потребуется добавить согласованный Uint8Array категорий, сохранить соответствие индексов и включить новые буферы в учёт памяти. Передавать координаты заново при смене темы не нужно. Сортировка по тяжести также не должна разрушать выбор по исходному индексу; её проектируем отдельно, а не переставляем массивы произвольно.

Для доли тяжёлых последствий надо согласовать знаменатель при фильтре последствий: выбранные только тяжёлые ДТП дают 100% по определению. Исходный count и знаменатель должны быть видны в панели; нельзя выдавать такую долю за независимую характеристику территории. Население 2025 не является знаменателем отдельной H3-ячейки: у нас нет населения по ячейкам, а ДТП включают приезжих участников.

Предлагаемый результат ближайшего шага: согласовать общую тему и постоянную панель. Новую аналитику ячеек испытать отдельно. Отчёты 03–04 далее разбирать следующей парой — там основной набор аналитики и сравнение регионов.

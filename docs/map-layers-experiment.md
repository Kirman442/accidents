## Исправление исчезновения и нагрузки при zoom

После проверки пользователем подтверждено: прежний effect очищал hex и пересоздавал worker при изменении разрешения. Теперь worker живёт весь срок текущего отбора; координаты передаются один раз. Кеш индексов двух разрешений с вытеснением; устаревшие запросы отбрасываются, новый расчёт может отменить незавершённый старый. При zoom предыдущий hex остаётся до готовности нового, не меняется на пустую карту. При новом годе/отборе прежние ячейки не подставляются как новый результат.

Камера обновляется сразу, агрегация/окно — после250мс покоя. Авто использует раздельные пороги10.2/9.8. Геометрия готовится только для окна с запасом в половину viewport по сторонам, тогда как индекс/сумма считают весь отбор. В панели отдельно указаны все непустые ячейки и подготовленные для окна. Это сокращение отрисовки, не выборка ДТП. Сохранён постоянный id слоя deck.gl, изменение зазора явно обновляет геометрию.

Измерения данного браузера: Германия273007, первый H3 5 индекс1377мс/геометрия61мс; H3 6 индекс1332мс/геометрия255мс. Повторный H3 5 использовал кеш, геометрия46мс (показанная длительность индекса историческая, не повторный расчёт). Berlin13280/H3 8: индекс77мс, геометрия42мс;1019ячейкa всего,768подготовлены для окна до отдаления. Это время worker, не GPU-бенчмарк и не гарантия FPS. При смене разрешения в браузере проверено сохранение прежнего слоя с уведомлением, отдаление Berlin не убрало слой, консоль чистая. ESLint прошёл; тест worker проверяет кеш, culling с сохранением общего числа, игнорирование устаревшей работы и сброс кеша при новом отборе. Снимок: UAD_data/map-layers-stable-zoom.png.

Первый индекс большого отбора всё ещё стоит около1.3с; на слабом устройстве/очень мелком разрешении возможны дальнейшие ограничения. Плавность GPU и политика разрешений остаются предметом проверки. Не утверждать, что любая нагрузка полностью устранена.

## Реализация и назначение

Реальные Arrow/Brotli2020–2025 через существующий FileLoader/RuntimePool. SHA256/сводки проверяются прежним загрузчиком, итог показывается после полного года. Выбор земли, группы участников и последствий применяет реальные worker-маски. Это сокращённый редактор для эксперимента, не замена согласованных фильтров макета.

Авто: H3 при zoom<10, ScatterplotLayer от10. Порог10 — кандидат, не окончательное правило. H3 resolution5/6/7/8 по порогам zoom6/7.5/9; ручной выбор доступен. H3 в отдельном worker, суммы проверяются на сохранение каждого ДТП, включая совпавшие координаты. Пустые ячейки не рисуются. Географические полигоны могут пересекать административную границу; подсчёт при выборе земли включает только записи выбранной земли.

Прозрачность и зазор10%/20% — визуальные параметры. Зазор уменьшает только нарисованный полигон относительно центра, исходная географическая ячейка и ее подсчёт не меняются. Цветовые интервалы фиксированы:1–9,10–49,50–99,100–499,500–999,1000+. При изменении разрешения меняется площадь, напрямую сравнивать числа разных размеров нельзя. Выбор ячейки открывает число/точную площадь ячейки и явную кнопку приближения; выбор сам не двигает камеру.

HeatmapLayer отдельным режимом, SUM, вес каждого ДТП1, сглаживание30px, текстура1024. Шкала автоматически нормируется, цвет не является точным числом ДТП или риском поездки. Географический радиус сглаживания меняется с масштабом. Это эксперимент плотности, а не окончательно согласованная методика.

Точки бинарные, без случайной выборки; выбрана основная запись через picking, сведения читаются из прежних workers. Для конечной версии ещё нужны выбор нескольких точек под кликом, доступный список, карточка/уведомления согласованного дизайна, проверка stale selection при переходах разрешения и гистерезис Авто. Кластеры пока только в списке экспериментов. При смене года эксперимент пересоздаёт загрузчик — здесь не проверяется многолетний LRU-продуктовый сценарий.

Границы BKG, обе CARTO-подложки. Элементы эксперимента не объявлять законченным UI/UX. Особенно сравнить плотную сетку на всей стране, читаемость низких цветов, разрешение для земли/города и переходный zoom.

## Стенд проверки гипотез Performance Optimization · 14.10.2026

В существующую страницу добавлены контрольные варианты:
- stable/copy: стабильные ссылки или копии XYZ/cellData на каждом обновлении камеры;
- visible/remove: сохранение посещённых слоёв или удаление невидимых;
- H3HexagonLayer/PolygonLayer: стандартная H3-геометрия или создание координат через cellToBoundary в getPolygon;
- native DPR/1: разрешение только deck.gl (подложка остаётся прежней).

Три сценария по 7 секунд: pan, zoom, hex/points switch. Первая секунда исключена из RAF-статистики, затем 6 секунд наблюдения. Камера и режим восстанавливаются. Все основные контролы блокируются во время прогона. JSON содержит параметры, задержки RAF (mean/p95/max/>50ms), синхронное CPU-время между onBeforeRender/onAfterRender за весь прогон, long tasks при поддержке браузера, счётчики копирования данных, запросов worker и getPolygon. JS heap необязателен, не означает GPU-память. История последних 20 прогонов сохраняется только в состоянии страницы до обновления.

Эти замеры НЕ разделяют подготовку атрибутов и загрузку в GPU, НЕ измеряют завершение GPU-команд и НЕ являются FPS видеокарты. Для точного разделения нужны profiler/trace и GPU timer queries при поддержке устройства. В RAF участвуют React, MapLibre и deck.gl. Граница кадра RAF не гарантирует фактическое представление кадра. CPU render не включает все update/attribute задачи. Сохранённые невидимые слои могут обновлять данные и держат ресурсы; JSON записывает visited. Для сравнения одного движка начинайте с одинакового набора посещённых слоёв, лучше свежей страницы. PolygonLayer в контроле не поддерживает coverage: используйте зазор 0 для визуального сравнения.

Первый smoke test, Германия 2025, 273007 ДТП, zoom4.6, GPU, pan:
- stable: RAF mean16.7/p9516.8/max21.9ms, >50ms0, CPU render mean1.26ms, dataBuilds0, workerRequests0;
- copy: RAF mean53.1/p95100.1/max166.6ms, >50ms56, CPU render mean31.04ms, dataBuilds130, workerRequests0.

Это единичные наблюдения в текущем браузере, не общий норматив и не чистый GPU-бенчмарк. Контроль PolygonLayer/copy на H3res4: getPolygon185625 вызовов за один pan-прогон, workerRequests0. Это показывает затраты геометрии, которые кеш подсчёта не устраняет. Старый worker с пересылкой массивов полигонов полностью не воспроизводится: контроль выделяет гипотезу пересоздания geometry на клиенте.

Документация: https://deck.gl/docs/developer-guide/performance . Реализованы stable data/useMemo, updateTriggers, binary positions, visible, worker counts, уменьшение DPR. Ещё не реализованы полный zero-copy, измерение отдельных upload-фаз, точная GPU-память и адаптивный выбор движка по оборудованию.
Сценарий zoom в итоговом стенде ступенчатый: удерживает каждый масштаб 500 мс, чтобы debounce 250 мс действительно успевал запускать обновление размера. Старый индикатор elapsed от snapshot до события GPU удалён как вводящий в заблуждение; вместо него дата последнего события. Прямой upload/GPU timing остаётся открытой задачей.
Повторный финальный прогон после изменений: GPU stable pan mean17.0/p9516.8ms, copy pan mean54.7/p95100.3ms, dataBuilds0 против130. Итоговые JSON/скриншот: UAD_data/map-layers-benchmark.json и map-layers-benchmark.png. Контролы возвращены stable/visible/H3/native DPR.

## Документация Building Apps / Composite / ScreenGrid · 14.10.2026

Прочитаны:
- https://deck.gl/docs/developer-guide/building-apps
- https://deck.gl/docs/developer-guide/custom-layers/composite-layers
- https://deck.gl/docs/api-reference/aggregation-layers/screen-grid-layer
- https://deck.gl/examples/screen-grid-layer
- официальный examples/website/screen-grid/app.tsx из ветки9.4-release (View Code).

Building Apps: ESM/tree-shaking и выбор необходимых модулей относятся к объёму загрузки/старту, не гарантируют рост FPS. Описанный visgl:webgl-only относится к9.4; установленная версия проекта9.1.8, включать условие как будто оно уже поддержано нельзя.

CompositeLayer: кандидат будущего AccidentsLayer с points/hex/screen-grid/selection и общими исходными buffers. getSubLayerProps для ids/visible/pickable/opacity/updateTriggers; getPickingInfo для корректной связи событий с исходными ДТП. Обёртка сама не отменяет aggregation и не гарантирует отсутствие отдельных GPU-буферов в дочерних слоях. Не переписывать ради обещанного ускорения без замеров.

ScreenGridLayer: квадратные bins фиксированного размера в пикселях; географическая площадь меняется с масштабом, границы зависят от viewport. События viewportChanged вызывают повторную агрегацию, подтверждено в node_modules/@deck.gl/aggregation-layers/src/screen-grid-layer/screen-grid-layer.ts версии9.1.8. GPU reaggregation не означает медленную работу: нет CPU-worker полигонов, рисуются экранные bins. В GPU picking доступны агрегированные значения, pointIndices/points только CPU. ## CPU/GPU aggregation и DataFilterExtension · 14.10.2026
Источники: https://deck.gl/docs/api-reference/aggregation-layers/overview#cpu-vs-gpu-aggregation ; https://deck.gl/docs/api-reference/extensions/data-filter-extension . Прочитаны вместе с установленным кодом9.1.8.

- CPU агрегация примерно линейна по N; GPU имеет overhead подготовки/загрузки, но документация указывает преимущество для крупных наборов >100K. Это не норматив нашего устройства: опубликованные числа измерены на2016 MacBook Pro/R9M370X2GB, не наш стенд.
- GPU память зависит от всех возможных bins, включая пустые, CPU от занятых. Для sparseGermany и малого fixed radius считать bins/ресурсы, не только число ДТП.
- GPU не возвращает список pointIndices в ячейке; для детализации worker локального отбора по геометрии/viewport по запросу. CPUAggregator deck.gl и наш H3 worker это разные реализации, не переносить коэффициенты ускорения.
- DataFilter: stable data + filterRange/filterCategories, 1-4 numeric +1-4 categorical dimensions, GPU attributes. Меняется отбор, а не XYZ; GPU aggregation всё равно пересчитывает суммы. Категории позволяют несмежные месяцы/дни/часы; нельзя заменить их единственным min/max при произвольном выборе. Шесть участников со состояниями без/любой/с требуют отдельного кодирования, нельзя просто представить их одним взаимно исключающим видом.
- Альтернативный общий маршрут для всех наших сложных фильтров: worker считает точную маску; GPU получает filterValue0/1 по всему стабильному набору, filterRange[1,1]. XYZ остаётся неизменным, обновляется лишь mask buffer. CPU-отбор при этом остаётся; не называть это полностьюGPU filtering.
- CPU fallback агрегаторов не применяет GPU extensions: обязательно согласованный fallback с CPU mask/filter и точными итогами, иначе скрытые на карте точки попадут в суммы.
- countItems/onFilteredItemsChange опциональны; не заменять точную аналитику этими событиями без проверки семантики/counts/readback. Composite callbacks могут вызываться по sublayer; не складывать дубликаты.
- Важно противоречие источников: extension limitations отмечает HexagonLayer как not supported, overview говорит оGPU extensions broadly. В9.1.8 HexagonLayer.createAggregator использует super.getShaders и inheritedAggregationLayer передаёт shaderModuleProps; это основания тестировать, а НЕ доказательство корректной динамической фильтрации. Не объявлять Hexagon+DataFilter поддержанным без интеграционного теста. ScreenGrid GPU явно указан supported. Для H3HexagonLayer готовые counts не пересчитываются от скрытия полигонов: фильтровать исходные ДТП иповторно агрегировать.

Следующий A/B (не реализован): сначала ScreenGrid GPU+stable XYZ+getWeight1/SUM; затем DataFilter по одному месяцу/категории и сравнение точных count с worker, исходные координаты неизменны. Отдельно проверять динамические filterRange/filterCategories, GPU backend, CPU fallback и выделение ячеек. Hexagon+DataFilter отдельная проверка совместимости. Код в этой фазе не менялся.
